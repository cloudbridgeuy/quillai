# UI language

Approach for GUZ-822. English and Spanish UI copy live in typed tables and are formatted with `Intl`. No new dependencies. The helper in `app/src/i18n/messages.ts` proves the shape. It is not wired into components.

## Separate from the manuscript

UI language is separate from manuscript language and from series language. The rules engine, and spell check, follow the series language (see `docs/rules-engine.md`), not this UI locale. AI prompt language is a separate ticket (GUZ-829). Changing the UI locale must not change chapter text, lore, or prompts.

## Tables

One flat object per locale in `app/src/i18n/messages.ts`. Keys are dotted ids (`action.save`). The only nested value is a plural object. English (`en`) is the source shape. Spanish is:

```ts
const es = { /* same keys as en */ } as const satisfies MessageShape<typeof en>;
```

`MessageShape` requires every English key. A string stays a string. A plural stays a plural object with a required `other` and optional `zero`, `one`, `two`, `few`, and `many`. A missing key, an extra key, or a string/plural mismatch is a type error.

The five keys shipped here (`action.save`, `greeting.hello`, `chapter.count`, `draft.words`, `edit.summary`) are samples. They are not product copy.

Translators edit `messages.ts` only. There is no extraction file and no second catalog.

## Compile-time check

Use the compiler pinned by `app/bun.lock`, TypeScript 5.8.3:

`cd app && ./node_modules/typescript/bin/tsc --noEmit -p .`

A global `tsc` is a different binary and is not this check. On the shipped tables, `src/i18n/` has no errors under that command.

Breaking `es` on purpose, then restoring it, reports an error in `messages.ts`: TS1360 when `action.save` is missing, TS2353 for an extra key, and TS2322 when a string key is a plural object. `messages.test.ts` also checks at runtime that `es` and `en` have the same keys and the same string-vs-plural kind.

## Lookup

```ts
formatMessage(locale, key, values?, catalog?)
```

`catalog` defaults to the shipped `{ en, es }` tables. Callers pass a locale string. The function does not read the browser, storage, or React. There is no module-level current locale.

`resolveLocale` trims and lowercases the tag. The Spanish tag is `es`. Any regional tag `es-…` (`es-ES`, `es-MX`, `es-419`) resolves to `es`. Every other tag resolves to `en`. `Intl` uses the resolved tag, so `es-MX` formats numbers as `es` (`1234,5`), not as `es-MX` (`1,234.5`).

## Interpolation

Placeholders are `{identifier}` (`{name}`, `{count}`, `{when}`, `{price}`). No ICU MessageFormat syntax and no extra parser.

| Value | Rendering |
|---|---|
| `string` | Inserted as plain text. The result is not scanned again. |
| `number` | `Intl.NumberFormat(locale)` |
| `Date` | `Intl.DateTimeFormat(locale, { dateStyle: "medium", timeZone: "UTC" })` |
| `{ amount, currency }` | `Intl.NumberFormat(locale, { style: "currency", currency })` |

A placeholder with no value stays as `{name}` so the gap is visible. A `{` that is not an identifier placeholder is left as written. There is no escape syntax. The helper returns plain text. Callers must not assign it to HTML. A bad currency code throws, the same way `Intl.NumberFormat` does. Missing keys and locales do not throw.

## Plurals

`Intl.PluralRules(locale).select(count)` picks the category. `count` has to be a finite number. The chosen string is then interpolated, so `{count}` is the locale's formatted number.

A category the message does not define uses `other`. Spanish selects `many` for `1000000`; the sample has no `many`, so the `other` line is used (`1.000.000 capítulos`). A missing `count` uses `other` and leaves `{count}` in place. A non-finite `count` also uses `other`, then `{count}` is formatted by `Intl` (`NaN`).

## How components get the locale

Not wired in this ticket.

The UI language choice is stored in the browser. When it is wired, a React context at the app root reads that stored choice, passes it into `formatMessage`, and sets `document.documentElement.lang` to the resolved locale (`en` or `es`). The helper stays free of React.

## Fallback

1. `es` and regional Spanish tags (`es-…`, case-insensitive) use the Spanish table and `es` for `Intl`. Any other tag, including `en-US` and `fr`, uses the English table and English `Intl`.
2. A key missing on the active table uses the English message. Numbers and dates in that string still use the active locale, so a Spanish UI keeps Spanish digits when the words fall back.
3. A key missing on the English table too returns the key string. The helper does not throw.
4. A missing plural category uses `other`.

## Length

Spanish UI copy runs about 20–30% longer than English. From the 1100px breakpoint, `.editor-drawer` is `width: 300px` (`app/src/index.css`), with 12px labels and 13px body text. `overflow-wrap: anywhere` is already set. Longer labels can still wrap onto extra lines or crowd a row. What to change is an open question.

## Open questions

1. The right drawer is 300px wide at 1100px and Spanish runs longer. Should it grow, wrap, or use shorter Spanish labels?
2. Is UI money always USD, matching catalog prices, or a currency the author picks?
3. Which date style and time zone should UI dates use? The proof uses `dateStyle: "medium"` and `timeZone: "UTC"` so the calendar day does not follow the machine zone.
4. Must a locale table include every plural category that locale can select (`many` for Spanish at 1,000,000), or is falling back to `other` enough?
