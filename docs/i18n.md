# UI language

Approach for GUZ-822. English and Spanish UI copy live in typed tables and are formatted with `Intl`. No new dependencies. The helper in `app/src/i18n/messages.ts` proves the shape. It is not wired into components.

## Separate from the manuscript

UI language is separate from manuscript language and from series language. The rules engine, and spell check, follow the series language (see `docs/rules-engine.md`), not this UI locale. AI prompt language is a separate ticket (GUZ-829). Changing the UI locale must not change chapter text, lore, or prompts.

## Tables

One flat object per locale in `app/src/i18n/messages.ts`. Keys are dotted ids (`action.save`). The only nested value is a plural object. English (`en`) is the source shape. Spanish is:

```ts
const es = { /* same keys as en */ } as const satisfies MessageShape<typeof en>;
```

`MessageShape` requires every English key. A string stays a string. A plural stays a plural object with a required `other` and optional `zero`, `one`, `two`, `few`, and `many`. A missing key, an extra key, or a string/plural mismatch is a type error on a compiler that can check this project.

The five keys shipped here (`action.save`, `greeting.hello`, `chapter.count`, `draft.words`, `edit.summary`) are samples. They are not product copy.

## Compile-time guarantee is unproven

`cd app && bunx tsc --noEmit -p .` uses TypeScript 4.9.5. That compiler rejects `app/tsconfig.json`: `module: "Preserve"` and `moduleResolution: "bundler"` are not valid options (TS6046), then reports hundreds of unrelated module errors. `messages.ts` is in that run and has no error of its own, because the shipped Spanish table is complete. `messages.test.ts` fails only with the same `bun:test` resolution error as the other tests (TS2792). A missing Spanish key was not part of that run. This ticket does not upgrade TypeScript. The compile-time guarantee is unproven.

The same `satisfies MessageShape<typeof en>` pattern, compiled by itself with TypeScript 4.9.5, reports TS1360 for a missing key, an extra key, and a string/plural mismatch. That side check is not `tsc --noEmit -p .`.

`messages.test.ts` checks at runtime that `es` and `en` have the same keys and the same string-vs-plural kind. That is not a type error.

## Lookup

```ts
formatMessage(locale, key, values?, catalog?)
```

`catalog` defaults to the shipped `{ en, es }` tables. Callers pass a locale string. The function does not read the browser, storage, or React. `resolveLocale` maps any tag other than exact `es` to `en`. There is no module-level current locale.

## Interpolation

Placeholders are `{identifier}` (`{name}`, `{count}`, `{when}`, `{price}`). No ICU MessageFormat syntax and no extra parser.

| Value | Rendering |
|---|---|
| `string` | Inserted as plain text. The result is not scanned again. |
| `number` | `Intl.NumberFormat(locale)` |
| `Date` | `Intl.DateTimeFormat(locale, { dateStyle: "medium", timeZone: "UTC" })` |
| `{ amount, currency }` | `Intl.NumberFormat(locale, { style: "currency", currency })` |

A placeholder with no value stays as `{name}` so the gap is visible. A `{` that is not an identifier placeholder is left as written. There is no escape syntax. The helper returns plain text. Callers must not assign it to HTML. A bad currency code throws, the same way `Intl.NumberFormat` does. Missing keys and locales do not throw.

## Plurals

`Intl.PluralRules(locale).select(count)` picks the category. `count` has to be a finite number. The chosen string is then interpolated, so `{count}` is the locale's formatted number.

A category the message does not define uses `other`. Spanish selects `many` for `1000000`; the sample has no `many`, so the `other` line is used (`1.000.000 capítulos`). A missing `count` uses `other` and leaves `{count}` in place. A non-finite `count` also uses `other`, then `{count}` is formatted by `Intl` (`NaN`).

## How components get the locale

Not wired in this ticket.

When it is wired: a React context at the app root holds the active UI locale and passes it into `formatMessage`. The root sets `document.documentElement.lang` to that locale. The helper stays free of React. Where the stored choice comes from is an open question below.

## Fallback

1. Any locale tag other than exact `es` uses the English table and English `Intl` (`en-US`, `es-MX`, `ES`, and `fr` included).
2. A key missing on the active table uses the English message. Numbers and dates in that string still use the active locale, so a Spanish UI keeps Spanish digits when the words fall back.
3. A key missing on the English table too returns the key string. The helper does not throw.
4. A missing plural category uses `other`.

## Length

Spanish UI copy runs about 20–30% longer than English. From the 1100px breakpoint, `.editor-drawer` is `width: 300px` (`app/src/index.css`), with 12px labels and 13px body text. `overflow-wrap: anywhere` is already set. Longer labels can still wrap onto extra lines or crowd a row. What to change is an open question.

## Open questions

1. Where does the UI language choice live: the browser language, a Settings control, this browser only, or the account? What is the default before a choice is stored?
2. Which Spanish tag should the table and `Intl` use: `es`, `es-ES`, `es-MX`, or `es-419`? In Bun 1.4.2, `es` formats `1234.5` as `1234,5` and USD as `1234,50 US$` (narrow no-break space). `es-MX` and `es-419` format `1,234.5` and `USD 1,234.50`. Should a regional tag such as `es-MX` use the Spanish table?
3. The right drawer is 300px wide at 1100px and Spanish runs longer. Should it grow, wrap, or use shorter Spanish labels?
4. Is UI money always USD, matching catalog prices, or a currency the author picks?
5. Which date style and time zone should UI dates use? The proof uses `dateStyle: "medium"` and `timeZone: "UTC"` so the calendar day does not follow the machine zone.
6. Must a locale table include every plural category that locale can select (`many` for Spanish at 1,000,000), or is falling back to `other` enough?
7. Is editing `messages.ts` enough for both languages, or do translators need a path that is not a TypeScript edit?
